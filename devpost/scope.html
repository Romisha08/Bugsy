Project scope · approved

Bugsy

A Python dependency repair assistant for developers, students, and hackathon participants. Upload or paste a requirements.txt, choose a Python version, review parsed requirements, get evidence-backed fixes, and verify them in Nebius.

Approved scope · proof of concept

The distinctive idea

Bugsy ties repair recommendations to compatibility evidence and actual sandbox checks. It reports dependency resolution, installation, and import checks separately; successful dependency checks never prove the user's application works.

Who it helps

Developers, students, and hackathon participants facing Python dependency conflicts or broken environments.

Why build it

The learner regularly faces Python install failures and wants to make Bugsy work while learning about Nebius and sandbox execution.

The end-to-end workflow

Parsing must be reliable before compatibility analysis begins. Verification is limited to the actual Nebius environment.

The sandbox OS and Python version are shown. Results do not guarantee compatibility on a local machine or another operating system.

In-scope features
  • Upload or paste requirements.txt; no separate manual package-entry feature.
  • Select Python version and preview parsed names and version limits read-only.
  • Show malformed or unsupported lines with line number, original text, explanation, and correction request; block full analysis until corrected. Accept supported syntax and valid environment markers.
  • Use package metadata and a real resolver for evidence-backed conflict explanations and recommendations; account for supported OS-specific markers.
  • Use NVIDIA Nemotron through Nebius Token Factory for diagnosis and repair planning.
  • Verify dependency resolution, installation, and reliable import checks in Nebius; show its actual OS and Python version.
  • Show separate dependency, install, import, and project-test statuses. Project tests are always “not run—project code not provided” in the MVP.
  • Show a proposed-change summary and diff; require approval before offering a revised-file download. Preserve the original.
Out-of-scope features
  • Manual package entry and dependency formats beyond requirements.txt.
  • Project-code/test uploads and project-specific test execution.
  • Multi-agent orchestration, other programming languages, and a full VS Code extension.
  • A second full local verification engine.
  • OS target selection or cross-platform guarantees.
  • Direct changes to the uploaded file or user's local project.
  • Unnecessary paid external services.
Safety requirements
  • Dependency resolution, installation, and import checks run in the Nebius sandbox. Never run model-generated commands on the host.
  • First confirm the SDK with a harmless Python command. Keep sandbox integration behind a configuration flag.
  • Show unavailable, skipped, and failed checks clearly. Installation or import success alone cannot make the repair “fully verified” or prove the user's application works.
  • Preserve the source file. Download only after the proposal is ready and the user approves its summary and diff.
  • Show actual sandbox OS and Python version; limit claims to that environment.
  • Project-specific tests are not run in the MVP and are marked “not run—project code not provided.”
Acceptance criteria
  1. The user can upload or paste requirements.txt and select Python version; no OS selector or separate package entry.
  2. Before analysis, parsed requirements appear read-only. Unreliable lines show line numbers, original text, and clear explanations; full compatibility analysis pauses until a corrected source parses. Supported syntax and valid environment markers are not falsely flagged.
  3. Compatibility analysis uses metadata and a real resolver. Proposals include evidence and use Nemotron via Nebius Token Factory for diagnosis and repair planning.
  4. Resolution, installation, import, and project-test statuses appear separately with errors and pass/fail/skipped/not-run states. Project tests say “not run—project code not provided.”
  5. Imports run only for reliably mapped package names. The actual sandbox OS and Python version are displayed, and results are not represented as cross-platform guarantees.
  6. The original file remains unchanged. The user sees and approves a summary and diff before downloading the ready proposal.
  7. When Nebius is disabled or unavailable, no successful sandbox verification is claimed.
