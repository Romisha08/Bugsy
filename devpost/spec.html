How this works, in plain language

The browser accepts requirements.txt and a Python version. FastAPI checks every line and blocks analysis if it finds unsupported syntax. PyPI provides read-only package facts; uv resolves the dependency set only inside ConTree. Nemotron explains those facts and may organize repair ideas, but Bugsy validates each proposed version against evidence and a real resolver.

When asked, the API sends the proposed file to a Nebius ConTree sandbox. Fixed application-owned steps run there and return separate resolution, installation, and import results. The user reviews and approves the exact diff before downloading. The original upload is never changed.

Supported targets map to images as follows: Python 3.10 → python:3.10-slim, 3.11 → python:3.11-slim, 3.12 → python:3.12-slim, 3.13 → python:3.13-slim, and 3.14 → python:3.14-slim. These mappings do not prove provider availability. Before uv setup or dependency resolution, Bugsy checks the actual Sandbox sys.version; missing, malformed, or mismatched runtime data cannot result in a successful resolution status.

Core rule: the model explains evidence; the resolver and sandbox provide the compatibility checks.
Access check: the historical root test_sandbox.py smoke command succeeded with contree-sdk==0.3.6. That is separate from the production adapter, which uses contree-client==0.4.1. Provider availability and actual runtime remain unverified for every mapped target.

Recommended stack and tradeoffs

React + TypeScript + Vite

Matches your choice and suits the report-focused UI. The browser calls Bugsy's API; it never holds service keys.

Python 3.12 + FastAPI + Pydantic

Python 3.12 is Bugsy's backend runtime. Sandbox compatibility targets are Python 3.10–3.14 with explicit target-to-image mappings listed above.

PyPI + uv

Metadata is evidence; uv is the actual resolver. Alternate OS and marker reasoning has documented limits.

Nemotron via Token Factory

Explanation and ranking only. Candidate versions pass deterministic evidence and resolver checks. The configured account currently lists five Nemotron IDs, and a Super model completion succeeded. Keep the ID configurable.

ConTree + local stub

The production adapter uses contree-client==0.4.1; the separate root test_sandbox.py uses contree-sdk==0.3.6. ConTree alone runs real resolution, installs and imports. The test stub may simulate success or failure for UI/tests, but all results are marked simulated; it never claims verification.

Optional hosting

Vercel for Vite and Render for FastAPI are documented options. Local demo is simpler; separate hosting needs CORS and backend secrets.

Bugsy API outline

These are proposed Bugsy routes, not Nebius endpoints. JSON schemas are implemented with Pydantic. Uploads use multipart form data.

POST /api/v1/requirements/parse

Accept one upload or pasted text and selected Python version. Return parsed package, constraint, marker and line data. Unsupported lines return 422 with the original line and action.

Request: {"text":"numpy<2\npandas==2.2.0\n","python_version":"3.12"}
200: {"source_id":"req_123","parse_status":"parsed",
 "requirements":[{"line":1,"name":"numpy","specifier":"<2","marker":null}],
 "warnings":[],"source_sha256":"..."}
422: {"error":{"code":"UNSUPPORTED_REQUIREMENTS",
 "details":[{"line":3,"original":"-e ./local_pkg",
 "reason":"Editable local paths are not supported."}]}}
POST /api/v1/analyses · GET /api/v1/analyses/{id}

Start an asynchronous analysis and poll its persisted analysis record. The report includes resolver status/version, evidence URLs and values, conflicts, proposal diff and explanation availability. SQLite preserves workflow records across backend restarts; interrupted running stages remain unknown/incomplete and are not automatically replayed.

POST request: {"source_id":"req_123"}
202: {"analysis_id":"ana_123","status":"queued",
 "poll_url":"/api/v1/analyses/ana_123"}

Report execution_mode is real or simulated. Checks: resolution / installation / imports / project_tests. Real status: passed / failed / not_run. Stub status: simulated, with simulated_outcome passed or failed.
Each: {status: "passed" | "failed" | "not_run", reason, output}

Illustrative schema only. No sample compatibility outcome is prepopulated.

POST verification · GET /verifications/{id}

Start verification for a proposal and poll. If ConTree is unavailable, affected real checks are not_run or incomplete and Bugsy makes no compatibility claim; it does not silently switch to the stub. Completed responses include execution_mode real or simulated, actual OS/Python for real runs, provider, exit codes and bounded logs. Simulated checks show a persistent SIMULATED label and never use real pass/fail badges. Project tests always say not_run — Project code not provided.

POST approval · GET download

Approve the proposal ID and exact diff hash. Download is available only after approval, as a requirements.txt attachment. The original upload stays unchanged.

One error shape: {"error":{"code":"...","message":"...","request_id":"...","retryable":true}}. Use 400 invalid shape, 413 oversized, 404 expired ID, 409 wrong workflow state, 422 unsupported syntax, 429 upstream limit, 503 unavailable integration, 500 unexpected failure. Never expose secrets, stack traces, or unbounded logs.

Safety rules

Only fixed app-owned commands run in ConTree. Never execute model text or user paths on the host. Limit size, time, output and concurrency; keep keys server-side; no secrets in sandbox; random IDs; strict CORS; exact diff approval; no direct project edits.
