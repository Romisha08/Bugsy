Look and feel

Blue-black base, readable high-contrast type, restrained rose and lilac accents, minimal bug detail, and monospace styling for technical values.

Core product rule

The parser preview is read-only. Unreliable lines pause full analysis until the source is corrected and parsed again.

Core journey

Every step stays focused on dependency analysis and repair; AI explanations support the evidence instead of replacing it.

Screen-by-screen behavior

1 · Empty dashboard and input
  • Show Bugsy branding with a minimal bug-inspired detail.
  • Make upload prominent; also provide drag-and-drop and a secondary paste option.
  • Allow Python-version selection; no OS target selector.
  • Explain the workflow and state that project-specific tests are outside the MVP.
  • Do not show sample compatibility data, fabricated scores, or completed verification.
2 · Parsed requirements review
  • Show parsed package names and version constraints in a read-only preview.
  • Keep parse success distinct from compatibility results.
  • For unreliable lines, show line number, original line, and explanation; ask for a corrected file and pause full compatibility analysis.
  • Allow file replacement and re-parse; no inline editing.
  • Recognize supported requirement syntax and valid supported markers without flagging them as errors.
3 · Compatibility report and conflict explanation
  • Use package metadata and a real resolver to explain affected packages, constraints, and why they conflict.
  • Show evidence behind compatible package-version or Python-version proposals.
  • Account for supported environment markers using the actual environment; make no cross-platform guarantee.
  • If no conflicts are found, scope the result to the analyzed environment.
  • AI explanations support technical findings; the main interface is not a chatbox.
4 · Proposed repair and verification
  • Keep proposals visually separate from sandbox-verified results.
  • On request, verify resolution, installation, and import checks inside Nebius.
  • Display the actual sandbox OS and Python version; make a selected/runtime mismatch explicit.
  • Show four statuses: dependency resolution, installation, import smoke test, project tests.
  • Only attempt import checks for reliable distribution-to-import mappings; otherwise mark skipped.
  • Project tests always read “not run—project code not provided” in the MVP.
  • Show errors and failed, skipped, or unavailable checks. Dependency checks do not prove the user's application works.
5 · Change review and download
  • Show a clear proposed-change summary and readable diff against the original.
  • Require user approval before enabling the revised-file download.
  • Preserve the uploaded or pasted source and never modify the user's local project.
  • Keep verification status beside the proposal so a proposed fix cannot be mistaken for a verified one.

States, errors, and boundaries

Empty, valid, and conflict-free states
  • First use: clean empty dashboard, no fabricated analysis.
  • Valid parse: parsed preview shown; compatibility not yet determined.
  • No conflicts: state that none were found for the analyzed environment only.
Malformed or unsupported requirements
  • Show affected line numbers, exact original lines, and plain-language explanations.
  • Pause full analysis; ask the user to upload or paste a corrected file.
  • Allow replace and re-parse; preserve the original.
  • Do not misclassify supported syntax or valid environment markers.
Resolver, AI, or sandbox error
  • Show the failed step and captured error; never substitute a made-up result.
  • If sandbox integration is disabled or unavailable, mark verification unavailable or not run and do not claim a verified repair.
  • Show each dependency check separately; a successful install or import cannot alone produce “fully verified.”
Project tests and cross-platform limits
  • Project-code and test uploads are not part of the MVP. Always report “not run—project code not provided.”
  • Dependency resolution, installation, and imports do not prove the user's application works.
  • Show the actual sandbox environment and limit compatibility claims to it.

Acceptance criteria

Observable proof of the MVP
  1. Upload or paste requirements.txt and select Python version. No separate package entry or OS target selector.
  2. Before analysis, show a read-only parsed preview. Unreliable lines include line number, original text, and explanation, and block full analysis until the source parses cleanly.
  3. Use package metadata and a real resolver to explain conflicts and provide compatibility evidence for proposed package/Python changes.
  4. Support NVIDIA Nemotron through Nebius Token Factory for diagnosis and repair planning.
  5. First confirm the Nebius SDK with a harmless Python command; run dependency resolution, installation, and import checks in the sandbox.
  6. Show actual sandbox OS/Python and separate resolution, installation, import, and project-test statuses with errors.
  7. Only attempt reliable import-name mappings. Project tests read “not run—project code not provided.”
  8. Do not label a repair fully verified from dependency checks alone or imply the user application works.
  9. Show a proposal summary and diff; enable download only after proposal readiness and user approval. Keep original unchanged.
  10. When sandbox is unavailable or disabled, clearly report no sandbox verification.
Product boundary: project-code testing is a possible later enhancement. Its technical design belongs in 4-spec; this PRD does not add code or test uploads.
